# 성능 측정 기록

측정일: 2026-10-20
환경: Intel Core Ultra 7 256V, RAM 16GB, Windows 11, Node v24.19.0, Microsoft Edge 155(헤드리스, puppeteer-core로 구동, 뷰포트 1680×1050)

> 헤드리스 브라우저는 GPU 가속이 제한될 수 있으므로, 실제 데스크톱 브라우저 수치와 다를 수 있습니다. 렌더링 FPS는 vsync 때문에 60에서 멈춥니다.

## 1. 엔진 단독 (`npm run bench`)

개체 수를 고정하고(번식, 사망, 대사 없음) 모든 개체가 항상 움직이는 최악의 이동 조건입니다. 월드는 밀도가 일정하도록 개체 수에 맞춰 키웠습니다.

|---:|---|---:|---:|---:|---:|
| 1,000 | 이동 | 0.109 | 9,190 | 306× | 0.03 |
| 1,000 | 시야 감지 | 0.325 | 3,079 | 103× | 0.02 |
| 5,000 | 이동 | 0.619 | 1,614 | 54× | 0.08 |
| 5,000 | 시야 감지 | 1.897 | 527 | 18× | 0.08 |
| 10,000 | 이동 | 1.267 | 789 | 26× | 0.11 |
| 10,000 | 시야 감지 | 4.563 | 219 | 7.3× | 0.18 |
| 20,000 | 이동 | 3.401 | 294 | 9.8× | 0.30 |
| 20,000 | 시야 감지 | 10.955 | 91 | 3.0× | 0.22 |
| 50,000 | 이동 | 8.543 | 117 | 3.9× | 0.33 |

- **병목은 시야 감지**로, 비용이 약 3배 늘어납니다. 개체마다 매 틱 최근접 질의를 하기 때문입니다.

## 2. 브라우저 종단 간 측정 (Worker + 렌더링 + React)

프리셋 A를 기반으로 개체 수를 늘린 설정을 '설정 불러오기'로 주입하고 각 배속에서 4초 동안 관찰했습니다. 표의 `long task`는 메인 스레드에서 50ms를 넘은 작업의 수입니다.

### 최적화 전 (단일 Path에 모든 개체)

| 개체 수 | FPS (1×) | long task (4초) | 최대 지연 |
|---:|---:|---:|---:|
| 1,000 | 58 | 0 | — |
| 5,000 | 10 | 44 | 135ms |
| 10,000 | 3 | 17 | 407ms |
| 20,000 | 1 | 9 | 1,655ms |

FPS가 개체 수의 **제곱**에 가깝게 떨어졌습니다. 원인은 서브패스 수만 개를 가진 Path 하나를 `fill()`하는 비용이 초선형이라는 점이었습니다.

### 최적화 후 (512개 단위 청크, 3px 미만 몸 단순화, 뷰포트 컬링)

| 개체 수 | 배속 | FPS | UPS (틱/초) | ms/틱 | 실제 배속 | long task |
|---:|---|---:|---:|---:|---:|---:|
| 1,000 | 1× | 60 | 30 | 0.20 | 1.0× | 0 |
| 1,000 | 10× | 58 | 299 | 0.19 | 10.0× | 0 |
| 1,000 | MAX | 56 | 9,739 | 0.10 | 325× | 3 |
| 5,000 | 1× | 60 | 30 | 0.79 | 1.0× | 0 |
| 5,000 | 10× | 60 | 293 | 1.04 | 9.8× | 0 |
| 5,000 | MAX | 60 | 1,293 | 0.76 | 43× | 0 |
| 10,000 | 1× | 60 | 30 | 1.97 | 1.0× | 0 |
| 10,000 | 10× | 60 | 299 | 1.77 | 10.0× | 0 |
| 10,000 | MAX | 58 | 579 | 1.70 | 19× | 0 |
| 20,000 | 1× | 60 | 30 | 4.14 | 1.0× | 0 |
| 20,000 | 10× | 58 | 229 | 3.72 | **7.6×** | 0 |
| 20,000 | MAX | 60 | 263 | 3.73 | 8.8× | 0 |

- 2만 마리에서도 렌더링이 60 FPS를 유지하고, 메인 스레드 블로킹은 0건입니다.
- 2만 마리, 10× 설정에서는 Worker가 따라가지 못해 실제 배속이 7.6×입니다. HUD의 '실속도' 칸이 이를 노란색으로 표시합니다.
- 프리셋 C를 MAX로 돌리면 약 1,400개 엔티티에서 실시간의 약 760배까지 나옵니다.

## 3. UI 개편 전후 비교 (2026-10-20)

같은 환경, 같은 설정(1× 속도로 실행, 패널은 건드리지 않음)에서 메인 스레드 사용률을 6초씩 3회 평균 냈습니다(Chrome DevTools Protocol의 `Performance.getMetrics`). 이전 UI는 커밋 `7cca50f`를 로컬에서 빌드했고(배포되어 있던 것과 번들 해시가 같음), 새 UI는 **배포된 GitHub Pages 사이트**에서 측정했습니다. 일시정지 값은 정지 버튼이 실제로 눌려 UPS가 0이 된 것을 확인한 뒤 쟀습니다. 헤드리스에는 GPU가 없어 캔버스가 소프트웨어 래스터이므로 절대값보다 비율을 보세요.

| 조건 | 이전 UI 스크립트 | 새 UI 스크립트 | 이전 스타일 재계산/s | 새 스타일 재계산/s |
|---|---:|---:|---:|---:|
| 1,000마리 실행 중 | 15.4% | **6.1%** | 4.3 | 1.0 |
| 1,000마리 일시정지 | 13.3% | **0.2%** | | |
| 5,000마리 실행 중 | 8.3% | **5.9%** | 4.2 | 1.0 |
| 5,000마리 일시정지 | 6.3% | **0.2%** | | |

- 새 캔버스는 이전보다 큽니다(1320×950 vs 1340×702, 확대율 0.84 → 1.06). 이 크기에서도 CPU가 줄어든 것은 HUD 격리와 변화 없는 프레임 건너뛰기 덕분입니다.
- 건너뛰기를 넣기 전에는 5,000마리 실행 중 스크립트 13.4%로, 이전 UI(8.4%)보다 **무거웠습니다**. 캔버스가 커지고 월드가 크게 그려지면서 늘어난 래스터 비용을 중복 그리기가 증폭했기 때문입니다.
- 5,000마리를 실행하면서 패널을 12번 여닫고 속도 슬라이더를 끄는 동안 60 FPS를 유지했고, 100ms를 넘는 메인 스레드 정지는 없었습니다(가장 긴 작업 80ms 안팎).

## 4. 남은 병목과 다음 단계 (우선순위 순)

1. **감지 비용**: 매 틱 대신 결정 시점이나 N틱마다 감지하도록 바꿉니다. 3배 가까이 빨라질 것으로 예상됩니다. 단 행동 규칙이 바뀌므로 문서도 갱신해야 합니다.
2. **먹이 격자 재구성**: 먹이는 대부분 정지해 있으므로 증분 갱신을 할 수 있습니다.
3. **틱 내 함수 호출**: `updateCreature`가 개체마다 설정 객체를 조회합니다. 종별 상수를 틱 시작 시 지역 변수로 캐시합니다.
4. **5만 마리 이상**: 다중 Worker(공간 분할)나 WASM(SIMD)을 검토합니다. 렌더링이 병목이 되면 WebGL 인스턴싱으로 전환합니다.

## 재현 방법

```bash
npm run bench                      # 엔진 단독 표
npx tsx scripts/bench.ts 1000,5000 # 특정 개체 수만
```
브라우저 측정에 쓴 puppeteer 스크립트는 프로젝트에 포함하지 않았습니다. 방법은 위 §2에 적은 대로 설정 파일을 불러와 HUD를 읽는 것입니다.
